# Plan: Firewalla gateway plugin (Store) + infra CLI

## Context
agents01–03 dropped off the 192.168.184.0/24 LAN onto a 192.168.122.0/24 scope and lost internet.
Fixing that needs router access, and today we only have a browser login that the automated browser
cannot complete. Ryan wants this solved as a product: a **Firewalla plugin on store.bytedesk.ai** that
any remote-gateway user can install to work with their own Firewalla from chat (MCP), API and CLI,
and that this infrastructure repo uses the same way.

Decisions made with Ryan:
- Version 1 covers the **MSP API and SSH to the box**. SSH writes are off by default and confirmed per action.
- Ryan's account is on a **paid MSP plan**, so the MSP API is available.
- Channels: the **Gateway Store plugin**, and the same binary used as a **CLI from this repo** via `infra run`.

Facts the design rests on:
- The MSP API (`https://<msp-domain>/v2`, header `Authorization: Token <pat>`) covers boxes, devices
  (rename only), rules (create/pause/resume/delete, block/allow only), alarms, flows, stats and target lists.
  It **cannot** change networks, VLANs or DHCP. Only SSH as `pi` can.
- The SSH password is shown in the app and rotates on reboot. Persistent changes go in
  `/home/pi/.firewalla/config/post_main.d/`.
- Store plugins are contract-v2 Go process plugins (model: `bytedesk-tmux-manager`). They are built by
  the TeamCity "Store plugin build v1" lane (`bytedesk-remote-gateway/.teamcity/Plugins.kt`), and an
  operator publishes them with the Store admin API.
- MCP tools come from implementing the `host.mcp.tool` point (`src/mcp_service_provider.go`,
  `src/mcp_tool_point.go`). No Store plugin does this yet, so Firewalla is the first.

## Approach
A new repo, **`ByteDeskAI/bytedesk-firewalla`** (plugin id `firewalla`), in Go and created from
`bytedesk-remote-gateway-plugin-template`. It builds **one binary in two modes**:
- `firewalla serve`: the gateway plugin process.
- `firewalla <noun> <verb> [--json]`: the CLI. It reads `FIREWALLA_MSP_DOMAIN`, `FIREWALLA_MSP_TOKEN`,
  `FIREWALLA_BOX_HOST` and the SSH agent from the environment, so `infra run` works unchanged.

Both modes call the same internal packages, so each operation is written once.

### Phase 0: Spike on Ryan's box (gates the SSH write design)
1. Ryan reads the SSH password from the app once. Install the `id_bytedesk` public key, plus a
   `post_main.d/10-bytedesk-authorized-keys.sh` script that re-adds the key after reboots and upgrades.
   Rollback: delete the script and the key line.
2. Read-only investigation: where networks, VLANs, DHCP scopes and reservations live (Redis keys and
   files under `~/.firewalla/config`), and how the app applies a change (which service reloads).
   Record the findings in `docs/box-internals.md` with the firmware version.
3. Go/no-go for SSH writes. If there is no safe, reloadable mechanism, version 1 ships SSH **read**
   tools only, and network moves stay in the app.

### Phase 1: Core packages
- `internal/msp`: a small typed client for the v2 endpoints above (no new dependencies, `net/http`),
  with cursor paging for flows.
- `internal/box`: SSH via `golang.org/x/crypto/ssh`.
  - Read: networks, DHCP leases, reservations, interfaces and routes.
  - Write (if Phase 0 is a go): assign a device to a network, add or remove a DHCP reservation.
  - Each write saves the prior value to plugin state first, so `undo` can restore it.
  - `bootstrap` takes the one-time password on stdin and installs the key and the persistence hook from step 0.1.
- `internal/tools`: one table of operations, each with a risk tier (read, write or destructive),
  that drives the MCP tools, the HTTP routes and the CLI commands.

### Phase 2: Gateway plugin surfaces (model: `bytedesk-tmux-manager/plugin.json`)
- `plugin.json` (generated by `cmd/manifest`, as in the template):
  - contract 2, kind process
  - identity "Firewalla", publisher `bytedesk`, pricing free
  - `implements`: `host.settings.section` and `host.mcp.tool`
  - routes `/api/…`
- **Settings section** (host-owned `secret` fields, so the plugin never stores the raw token in its own files):
  - MSP domain and API token
  - box host
  - an "Enable write tools" toggle (default **off**)
  - an "Enable SSH writes" toggle (default **off**)
  - The plugin generates an SSH keypair and stores it in `GATEWAY_PLUGIN_DIR/state` (mode 0600).
    The settings page shows the one-line bootstrap command.
- **MCP tools** from the operation table, for example `firewalla_devices_list`, `firewalla_rules_pause`
  and `firewalla_network_assign`. Write tools require `confirm: true` and return the rollback value.
- **HTTP API** `/p/firewalla/api/<noun>/<verb>`, using the same table.
- No UI panel in version 1. Add one when a user asks for a dashboard.

### Phase 3: Build and Store
- `scripts/ci/plugin-build-v1.sh`, copied from `bytedesk-tmux-manager/scripts/ci/plugin-build-v1.sh`
  (go test, native build, copy `plugin.json`).
- In `bytedesk-remote-gateway/.teamcity/Plugins.kt`, add `FirewallaPluginVcs` and a `FirewallaPluginBuild`
  based on the `PluginBuildV1` template, mirroring the TmuxManager entries.
- Publishing stays an operator step: `POST /v1/admin/packages`, then `PUT …/versions/<ver>/artifact?latest=1`
  with the TeamCity artifact. Ryan confirms each publish.
- Gitflow, `VERSION`, `CHANGELOG.md`, and a README with the install, settings and bootstrap steps.

### Phase 4: Infrastructure repo
- Infisical (Infrastructure, `global`, `/firewalla`): add `FIREWALLA_MSP_DOMAIN` and `FIREWALLA_MSP_TOKEN`
  (the token is created by Ryan in MSP Settings → MSP API).
- `registry/providers/firewalla-msp.json`: set access to `api, cli, ssh, browser`; update `firewalla-msp.md`
  with CLI usage.
- `registry/services/firewalla-msp.json`: add the token and domain references.
- New host `registry/hosts/firewalla-box.json`: ssh, `192.168.184.1`, user `pi`, `ssh-agent://id_bytedesk`.
- Route network and DHCP requests to `firewalla-msp` in `registry/routes.json`. Then run `infra sync`
  and `infra validate`.
- Also commit the Firewalla work from this session (the registry entries and the `bin/infra` schema change)
  with a CHANGELOG entry.

### Phase 5: Use it on the real problem
Run `infra run firewalla-msp -- firewalla network list`, find the 192.168.122.0/24 source, and propose
the move of agents01–03 back to 192.168.184.0/24 with its rollback. Apply only after Ryan's OK, then
verify they get .184 leases and can reach the internet.

## Verification
- `go test ./...`:
  - `internal/msp` against an `httptest` fake built from documented responses.
  - `internal/box` parsers against fixtures captured read-only in Phase 0.
  - The operation table: every write tool rejects a call without `confirm`.
- `plugin-sdk validate` and `plugin-sdk pack` pass on the staging output, and the TeamCity build is green.
- Install the packed plugin on the local gateway, and use agent-browser as a gateway user to open
  Settings → Firewalla and save the token. Check through the gateway MCP surface that the tools appear,
  `firewalla_boxes_list` returns Ryan's box, and the tools disappear when the plugin stops.
- CLI: `infra check firewalla-msp` resolves all references, and `infra run firewalla-msp -- firewalla boxes list --json` returns data.
- SSH: after a router reboot, key login still works, which proves the `post_main.d` hook.

## Risks to watch
- The point name is `host.mcp.tool` in the host but `mcp.tool` in the SDK (`bytedesk-sdk-dependencies/v2/plugin/points.go:28`).
  Confirm against the pinned SDK `v0.4.0-rc.11` before writing the manifest.
- The SSH internals are not documented and may change with firmware. Writes are gated on the
  firmware version recorded in Phase 0, and refuse to run on an unknown version.
