# TM-148 — a reclaimed task keeps the location its record knew

Committed at `f34b041`.

## The filed mechanism was wrong

AC1 said `tm start` on a task owned by a different **live** session silently overwrites ownership.
Measured in an isolated store:

| step | result |
|---|---|
| session A: `tm start TM-001` | in progress |
| session B: `tm start TM-001` | **REFUSED** — "claimed by main in /tmp/tmtest on master. Take it anyway with `--steal`" |
| claim after the refusal | still session A |

The interlock and its `--steal` escape both work. That criterion is accepted as met — confirming it
was worth doing, and it is now on the record instead of an assumption.

## The real defect is one step to the side

`park()` calls `release()`, so a parked task has **no claim to interlock on**. Reclaiming it is
legitimate. The silent part is what `start` then *writes*: `stamp()` overwrote the record's `branch`
and `worktree` with wherever the reclaimer stood.

    record before reclaim    session: "sessionA"   branch: "tm/TM-148-elsewhere"
    record after             session: "sessionB"   branch: "master"

That is exactly how TM-135 and TM-143 both came to read `branch: main` and the shared checkout while
their real work sat on a `tm/` branch in a worktree — and why four fields on each were corrected by
hand.

So the fix belongs in what `start` **writes**, not in what it may claim. Hardening the interlock
would have changed nothing, because the interlock was never bypassed.

## The fix

A location the record already carries is preserved when it disagrees with this checkout, and `start`
says so rather than doing it quietly. `--here` re-homes deliberately. The session still moves to the
reclaimer, because that part is true.

## Evidence

Six assertions in `test-store.sh`. Non-vacuity: with only `bin/tm` swapped to `HEAD`, in a real git
repository, the precondition passes and **exactly the three behavioural assertions fail**.

Gates: unit 1370/1370; store 146, hooks 65, hooks2 40, link 13, mcp 77, read 59, pool 19,
capability 22, concurrency 12, events 12, install 13 — all exit 0.

## Two mistakes of mine, recorded because both would have shipped a test that proved nothing

1. **The first version appended after the suite's summary line**, so its results printed but were
   neither counted nor gated by the exit code. Moved above it; the count went 140 → 146.
2. **The first non-vacuity check ran in a `git archive` tree.** There is no `.git` there, so
   `stamp()` omits `branch` entirely and the *precondition* failed — making the test look
   non-vacuous for an environmental reason rather than for the absence of the fix. That is rule 2 of
   `.claude/rules/verification-that-can-fail.md`, which this session wrote: *isolation is never
   free — ask what it removes.* Redone in a real repository with only `bin/tm` varying.
