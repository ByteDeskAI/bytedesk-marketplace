# EP-018 demo — two real orchestration runs in idle repositories

Run on 2026-09-09 in `bytedesk-bench`: clean tree, last commit nine weeks old, no `.bytedesk/`
before or after, no agents. Isolated tmux socket (`TMUX_TMPDIR=/tmp/aodemo`, `TMUX=''`), torn down
completely afterwards.

## What the demo was asked to do

Three agents — a `coordinates_only` conductor, a scribe and a checker — describing what the
repository is and verifying the answer against `README.md`. Deliberately trivial work: the point
was the coordination primitives EP-018 built, not the task.

## What actually happened, in order

1. `validate --spec` — **ok**.
2. `launch --dry-run` — **ok**: run dir, session name, per-agent argv and memory scope all resolved.
3. `launch` — **refused**: `TOPOLOGY_STARTUP_NOT_READY`, "Governed workflow launch requires a
   responsive repository lead and independent reviewer … no workflow panes were created." Correct,
   and it created nothing before refusing.
4. `lead ensure` — session created, supervisor started (pid recorded, `restarts: 0`, log path).
5. `reviewer ensure` — `TOPOLOGY_SESSION_START`: "Provider is not accepting startup instructions;
   session preserved."
6. `census --json` — **named the blocking condition without being asked**:

   ```
   c799df31  lead      -> attention   dispatchable: false   evidence: tail
   bbcf25f5  reviewer  -> attention   dispatchable: false   evidence: tail
   reason: Claude is waiting on its folder-trust question for this directory — nobody can answer it
           from here. Answer it once in a normal terminal (cd into the agent's cwd and run `claude`,
           choose "Yes, I trust this folder"), then launch again.
   ```

7. The supervisor ticked throughout: presence published (`schemaVersion 1`, 2 agents), census
   written, adaptive sleep backed off to 15 s on a quiet repo, `dispatchable: 0`.

## What worked, and it is most of the epic

- **The launch gate refused before creating anything.** No half-built run to clean up.
- **TM-111's guard held.** The trust modal draws `❯ No, exit`, so Enter would have exited the
  provider. The plugin did not type. It reported and preserved the session — exactly the behaviour
  the delivery state machine was designed around.
- **The census earned its place.** It turned a silent stall into a named state with the precise
  remedy, in one command, with zero model turns. That is the difference this epic set out to make.
- **Supervision behaved as specified.** One supervisor per repository, presence heartbeat, census
  on every tick, adaptive backoff, `dispatchable: false` for every agent that was not idle.
- **Teardown was clean.** Socket-scoped `kill-server`, supervisor stopped, repo back to zero dirty
  files, all eight state files for this repo removed, other repositories' state untouched, and the
  operator's five sessions unchanged before and after.

## What blocked it, and it is now TM-155

A governed launch needs a reviewer; the reviewer is deliberately never auto-approved
(`reviewer.mjs:145-146` forces `--restricted --safe-mode` and `auto_approve: false`, which is the
independence guarantee); and Claude Code shows a folder-trust modal the first time it opens any
directory — including each agent's own directory, which the plugin has just created. So the first
turn of every governed run in a fresh repository is a **human** turn, and it is not the human turn
the design chose to spend on `failover.consent`.

Nothing on this machine has ever trusted an agent directory: zero entries under any
`agent-orchestration/agents` path in `~/.claude.json` are trusted.

**I did not answer the trust prompt.** Pressing "Yes, I trust this folder" on the operator's behalf
is a consent decision, and fabricating it would defeat the check.

## To finish this demo

One action, once per agent directory, in a normal terminal:

```
cd <repo>/.bytedesk/agent-orchestration/agents/<agent-id> && claude
# choose "Yes, I trust this folder", then Ctrl-C
```

Then `lead ensure`, `reviewer ensure`, `launch` proceed unattended.

## Also found (both filed on TM-155)

- A long `TMUX_TMPDIR` fails as `error connecting to <path> (File name too long)` — the unix socket
  path limit is ~107 bytes. The error names the path but not the cause.
- A repo config template override must repeat the whole template, and its `prompt` resolves against
  the repo — so copying the documented default `./prompts/lead.md` points at a file that does not
  exist. Both that and a partial override fail with the same message, "Invalid lead prompt; refusing
  restart", which does not say which key was wrong.

# Second run — the trusted repository, and what actually blocks every launch

The first run left one claim untested: whether the folder-trust modal was the real blocker or an
artefact of choosing a repository Claude Code had never opened. It was the latter, and the second
run corrects it.

`bytedesk-tmux-manager`: clean tree, last commit two days old, **already trusted**. Same isolated
socket discipline, torn down after.

## What changed, and what did not

- **No trust modal.** `lead ensure` brought the lead straight up; the census read it as `working`
  within seconds. Trust is inherited by subdirectories of a trusted project root, so the agent's own
  directory needs no separate answer. **TM-155's original claim was too strong and is corrected on
  the task** — the modal blocks only a repository Claude has never been trusted in.
- **The launch was still blocked**, by something else entirely.

## TM-151, reproduced live with measurements

The reviewer session came up healthy — Claude Code v2.1.267, safe-mode banner, composer rendering
its placeholder hint:

```
❯ Try "fix lint errors"
```

Measured with tmux's own matcher against that exact pane, and a second pane showing
`❯ Try "create a util logging.py that..."`. `#{C/r:}` returns the line number of the first match,
or 0:

| pattern | result |
|---|---|
| shipped `ready.tmux_pattern` — `^\s*[│|]?\s*[>❯][^a-zA-Z0-9]*$` | **0** on both panes |
| candidate — `^\s*[│|]?\s*[>❯]([^a-zA-Z0-9]*$\|[^a-zA-Z0-9]*Try ")` | **12** on both panes |

**The consequence is bigger than a slow launch.** Readiness failing means the role session is never
*registered*: `role status reviewer` read `state: none, registered: false, alive: false` while the
session sat there idle. A governed launch requires a responsive lead *and* reviewer, so
`TOPOLOGY_STARTUP_NOT_READY` refuses every orchestration. **On this machine, with this pattern, no
governed run can start at all.**

And the two subsystems disagreed about the same pane: the census called the reviewer `idle` — "no
spinner and nothing waiting on a human" — while the launcher called it not ready. The census was
right.

## One more defect the retries exposed

Each failed `reviewer ensure` spawned a **new** session and left the previous one alive. Four
attempts left four abandoned reviewer sessions plus the lead. "Session preserved" is the right
answer to one failure; across retries it accumulates and nothing reaps them.

## Teardown, again verified

Socket-scoped `kill-server`, supervisor stopped, `.bytedesk/` removed, repository back to zero dirty
files, every state file for both demo repositories deleted, other repositories untouched, operator
sessions 5 before and 5 after.

## The honest verdict on this demo

Two runs, neither completing a message exchange between agents — and both failing for reasons worth
more than the demo would have been. The coordination layer this epic built behaved correctly
throughout: the launch gate refused before creating anything, the trust modal was never typed into,
the census named each blocking condition in one command with zero model turns, and supervision
ticked and published presence the whole time. What blocks it is one regex in
`providers/claude.json`, filed as TM-151 with a measured fix and its negative control
(`❯ half typed text` must not match, and does not).
