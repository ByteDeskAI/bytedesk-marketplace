Delivered from Bastion TM-019. Three minor findings faro raised on merged PRs (#152 TM-195, #154 TM-276); all still present on fix/ao-local-nats-autostart.

1. reviewer.mjs ~667 (TM-195): b64Closed reports an empty or one-character payload as closed, so a pane captured just after `AO_REVIEW <nonce> b64:` was printed is refused and the request is marked failed with no recovery. Fix: return false when the decoded text is empty/whitespace or the base64 is shorter than 4 chars, so a mid-print capture waits like an unclosed JSON prefix. Test: capture `AO_REVIEW <nonce> b64:` and expect RESPONSE_INCOMPLETE, not a failed request.
2. reviewer.mjs ~687 (TM-195): the b64 rejoin loop appends any following indented row made only of base64-alphabet characters, so a single word printed after the verdict corrupts a complete payload. Fix: stop appending once the payload ends in `=` or b64Closed(payload) is already true (or require continuation rows to match the preceding row width). Test: a complete b64 verdict followed by a one-word row decodes intact.
3. orch-transport.mjs ~410 (TM-276): only a repository supervisor refreshes last_fallback_at, and only for connections it holds, so a long-lived non-supervisor process on a fallback (e.g. an MCP server with the dead NATS_URL) can have its outage retired and then mint a second outage mail on reconnect. Fix: have each long-lived holder of a fallback refresh last_fallback_at periodically (e.g. from the transport heartbeat), or, if that is disproportionate, document that retirement reflects only supervisor and new-open activity and say why in your report. Test whichever you choose.
