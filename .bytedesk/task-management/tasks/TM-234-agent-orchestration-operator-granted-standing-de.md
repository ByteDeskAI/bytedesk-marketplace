Operator request 2026-09-24: the repository lead must be able to authorize integration itself, without the operator running each command.

Today `ao-topology manage integrate --authorized` and `manage record-landing --authorized` take a bare flag. When the lead passes it, the lead is attesting to an authority it grants itself. Claude Code's auto-mode safety check refused exactly that as "Self-Approval" when lead d60f0608 tried to record the landings of TM-214, TM-215, TM-221 and TM-224. The operator had to run the command by hand.

The fix is a standing delegation that the operator grants once, and the lead then exercises, with both recorded.
- `ao-topology delegate grant --to <agent-id> --repo <consumer> --scope integrate,record-landing [--expires <duration>] [--reason <text>]`
  - Run by the operator, never by the grantee: refuse when AO_AGENT_ID equals the grantee, or when the caller is a managed agent session.
  - Writes an append-only record under the state home: grantor (OS user), grantee, repo_id, scopes, created_at, expires_at, and an id.
- `ao-topology delegate list|revoke <id>`, run by the operator.
- When `manage integrate` and `record-landing` run without an explicit operator `--authorized`, they accept a valid, unexpired grant covering the caller's agent id, the repo and the scope.
  - The merge record stores `authorization {actor: <lead>, delegated_by: <grantor>, delegation_id, authorized: true}`.
  - `governedCompletion` keeps its current checks; it may display `delegated_by`.
- Every use is journaled and appears in task evidence.
- The grant never covers deploy, publish, push or spend. Those keep their separate authorization.
- Document the grant command in docs/repository-leads.md, so the operator can pair it with a Claude Code permission rule for the grant-exercising command if they choose.
