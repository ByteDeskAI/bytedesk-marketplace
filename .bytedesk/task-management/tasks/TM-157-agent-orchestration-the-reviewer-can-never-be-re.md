Found by running the demo through to the governed-launch gate with TM-151's fix applied, in bytedesk-tmux-manager. Both roles registered and alive; the launch still refused. The reviewer said why, in its own pane:

    I have no shell tool in this session (no Bash, and none available via tool search), and my
    standing instruction here is not to execute code - so I cannot run it. Until someone does, my
    recorded revision stays at the previous one. You can run it yourself by typing ! followed by
    that command in this session.

THE CONTRADICTION. `reviewer.mjs:145` launches the reviewer with `--restricted --safe-mode`, which removes Bash — that is the independence guarantee and it is correct. But responsiveness is proven by a NONCE ACK: the probe writes a nonce file, rings the pane, and waits for the agent to run `ao-topology prompt ack --nonce <uuid>`, which is a shell command. An agent with no shell cannot run it, ever. So:

    role status reviewer -> state: unresponsive, registered: true, alive: true, responsive: false

is not a transient state for the reviewer. It is permanent and structural. `launch` requires a responsive lead AND reviewer (TOPOLOGY_STARTUP_NOT_READY), so with the current design no governed orchestration can complete its gate even after TM-151.

This is the same shape as TM-135's defence-2 finding, one layer up: a liveness protocol that the agent it interrogates cannot physically speak. There it was `responsive: null` for non-singleton roles; here it is `responsive: false` forever for the one role the launch gate insists on.

WHAT THE FIX HAS TO DECIDE, and it is a design question rather than a patch:
- either the reviewer gets a way to ack that needs no shell (a file the provider can write with its own Write tool is not available either under safe mode; an ack the SUPERVISOR observes from the pane would work, e.g. the reviewer echoes AO_ACK <nonce> and the tick reads it from the capture),
- or the launch gate stops requiring a responsive reviewer and requires registered-and-alive, with responsiveness reported rather than gating,
- or the reviewer stops being launched under safe mode, which gives up the independence guarantee and should not be chosen lightly.

The lead is a different case and worth separating: it HAS a shell, so its unresponsive reading here is an ordinary missed probe (it was mid-turn when the nonce was rung, and the probe expires). That is a timing problem, not a structural one.
