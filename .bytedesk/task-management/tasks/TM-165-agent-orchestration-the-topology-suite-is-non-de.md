Three consecutive full runs of tests/unit/topology-*.test.mjs produced three DIFFERENT failure sets, and one of them was in the canonical checkout with no uncommitted changes at all.

    run 1, worktree      382 tests  1 fail   not ok 374 (supervisor survives losing its cwd)
    run 2, worktree      382 tests  2 fail   not ok 130 (reattach returns same session), 374
    run 3, CANONICAL     381 tests  3 fail   not ok 162 (CLI send persists notification), 369, 373

Every failing test touches tmux. Each passes 3/3 when its file is run alone, in both trees. So it is ordering or contention, not a defect in any one of them.

CONTEXT THAT MATTERS: 34 tmux sessions were live on the default socket during these runs — other agents' work, not the suite's. The tests are isolated per .claude/rules/tmux-test-isolation.md (blank TMUX, own TMUX_TMPDIR, socket-scoped kills), so this is not the 37-session incident repeating; it is more likely resource contention — pane creation, server startup latency, or a timing assumption that holds on an idle machine.

WHY THIS IS WORTH A TASK RATHER THAN A SHRUG. Every gate report in EP-018 — mine and the integrator's, across a dozen merges — was a SINGLE sample of this suite. '364/364' is true of the run it came from and is not a property of the revision. Nothing merged today is known to be wrong because of it, but the confidence those numbers carried was overstated, and the same discipline that says 'verified versus only read' says a one-sample green is not a green.

Related: .claude/rules/verification-that-can-fail.md §1 — a clean result that would look identical if the thing being checked were absent. A flaky suite is the same failure one layer out: a clean result that would have looked different if run again.
